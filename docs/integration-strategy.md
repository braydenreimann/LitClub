# LitClub API Integration Strategy

### OpenAPI TypeScript

LitClub uses **OpenAPI TypeScript** to enable the automatic conversion of OpenAPI schemas to TypeScript types.

#### How it works

The backend team will generate a new OpenAPI schema when new features or revisions are made to the API. A schema defines all of the API's request and response objects, as well as the paths to each of its endpoints. You are already familiar with Swagger, which provides a UI for viewing LitClub's OpenAPI schema (plus some added functionality for interactivity).

Through OpenAPI TypeScript, types on the frontend can be updated to reflect changes to the backend at an instant.

Here is an example of an object in the backend and its frontend counterpart:

##### C#
```csharp
public abstract class AddUserRequest
{
    public required string FirstName { get; init; }
    public required string LastName { get; init; }
    public required string UserName { get; init; }
    public required string Email { get; init; }
    public required string Password { get; init; }
    public string? Bio { get; init; }
    public string? ProfilePhotoUrl { get; init; }
    public List<string>? PreferredGenres { get; init; }
    public bool PrivateAccount { get; init; }
    public bool PublicInteractionRestricted { get; init; }
}
```

##### TypeScript
```TypeScript
type AddUserRequest: {
    firstName: string | null;
    lastName: string | null;
    userName: string | null;
    email: string | null;
    password: string | null;
    bio?: string | null;
    profilePhotoUrl?: string | null;
    preferredGenres?: string[] | null;
    privateAccount?: boolean;
    publicInteractionRestricted?: boolean;
};
```

#### The benefit?
This tool dramatically reduces the amount of time it would tike to manually do these conversions and removes the potential for human or LLM errors.

#### Where can I access these types?
All of the generated types are located at `frontend/schema/openapi-types.ts`, and were conviently placed there by Santa (backend).

To pull a specific type (component) from this file, it's pretty simple! The following is an example, which you can find in the file `books-mappers.ts`.

##### books-mappers.ts
```TypeScript
import { components } from "@/schema/openapi-types";
type BookResponse = components["schemas"]["BookResponse"];
```

In this example, the first line imports all of the components from the file `openapi-types.ts`. You should only do this once per file. The second line grabs the specific component `BookResponse`.

When you are trying to use a type in your code, follow the format `components["schema"]["{ObjectName}"]`.

When working on the frontend, you should reference the Swagger documentation for information on the components that are available to you.

### OpenAPI Fetch
openapi-fetch is a type-safe fetch client that pulls in your OpenAPI schema, and it works. In LitClub, a singleton client object is defined in the following file:

##### client.ts
```TypeScript
import createClient from "openapi-fetch";
import type { paths } from "schema/openapi-types";
import { env } from "config/env";

const API_BASE_URL = `http://${env.HOST_FROM_EXPO}:5112`;
console.error(API_BASE_URL);

export const client = createClient<paths>({ baseUrl: API_BASE_URL });
```
Let's look at how this client object can be used to send reqeusts to the API.

##### authContext.tsx
```TypeScript
  import { client } from 'client';
  import {
    toLoginRequest,
    type LoginRequestInput
  } from '../api-mappers/auth/auth-mappers';

  const signIn = async (input: LoginInput): Promise<boolean> => {
    try {
      const body = toLoginRequest(input);
      const { data, error } = await client.POST("/users/login", { body });

      if (error) {
        // Parse status codes on error object
      }

      const serialized = JSON.stringify(data);

      /* specific to auth */
      setSession(serialized);
      await AsyncStorage.setItem('session', serialized);

      return true;

      // Catch an exception, if thrown
    } catch (err) {
      console.error('Sign-in failed', err);

      return false;
    }
  };
```

1. The HTTP method is pulled directly from `client`.
2. You pass in your desired `path` to `GET()`, `PUT()`, etc.
3. TypeScript takes over the rest and returns helpful errors for anything missing or invalid.

Observe that this method is also importing a type and method from the file `auth-mappers`. Let's look at what this file contains.

#### Mapping Matters
In the file `auth-mappers.ts`, objects created by the frontend are mapped to objects created by the backend (generated by OpenAPI TypeScript). It's located in the directory `api-mappers/auth/`.

##### auth-mappers.ts
```TypeScript
import { components } from "schema/openapi-types"

// #1: Request object defined by backend
type LoginRequest = components["schemas"]["LoginRequest"];

// #2: Domain object defined by frontend
export type LoginInput = {
    email: string,
    password: string
}

// #3: Mapper function: domain object -> request object
export function toLoginRequest(input: LoginInput) {
    const loginRequest: LoginRequest = {
        userName: null,
        email: input.email,
        password: input.password,
    }

    return loginRequest;
}
```

In this example, observe that `LoginRequest` is pulled from the backend components generated by OpenAPI TypeScript. Next, `LoginInput` is defined. This type is to be used and defined by the **frontend**, and is not tightly coupled to the backend.

It should be noted that in the frontend, the user is never asked for a `userName`, so this value isn't stored. However, the `LoginRequest` object defined by the backend expects this field.

Fortunately enough, this field isn't actually required, so we can just set `userName` in the request object to `null`. This is done in the mapper function `toLoginRequest` which maps the *frontend* `LoginInput` object to the *backend* `LoginRequest` object.

#### The benefit?
Code written by the frontend only references the object defined by the frontend: `LoginInput`. The only method which is tightly coupled to the backend is `toLoginRequest`.

When changes are made to the backend, it's likely that some request and response objects will be modified. By defining mapper methods for frontend objects, we isolate breaking changes to the **mapper method**.

Suppose the field `userName` is removed from the object `LoginRequest` by the backend. Instead of digging through code to find all references of `userName`, the frontend dev can simply remove `userName` from the method `toLoginRequest`, and the app will start working again.

By using mapper methods, we prevent breaking changes from rippling throughout the entire system.

### A recipe for integration
In this example, let's go through the steps of integrating the UI for creating a new LitClub with the backend.

#### 1. Review Swagger API documentation

Find the request and response body schemas for `POST /litclubs`.

#### 2. Create a new mapper module

Create the directory and file `/api-mappers/litclubs/litclubs-mappers.ts`.

##### litclub-mappers.ts
```TypeScript
import { components } from "schema/openapi-types"

type AddLitClubRequest = components["schemas"]["AddLitClubRequest"]

// Type defined by frontend
export type AddLitClubInput = {
    name: string,
    ownerUserId: string,
    ownerUserName: string,
    description: string,
    preferredGenres: string[] | null,
    privateClub: boolean,
    memberUserIds: string[] | null,
}

// Mapper function
export function toAddLitClubRequest(input: AddLitClubInput) {
    const addLitClubRequest: AddLitClubRequest = {
        name: input.name,
        ownerUserId: input.ownerUserId,
        ownerUserName: input.ownerUserName,
        description: input.description,
        preferredGenres: input.preferredGenres,
        privateClub: input.privateClub,
        memberUserIds: input.memberUserIds
    }

    return addLitClubRequest;
}
```

#### 4. Define a domain model

Add a new LitClub domain model in `/domain/models.ts` (previously `interfaces.ts`).

*Note:* Domain models exist to represent the core business concepts of your application, cleanly and indpendent from backend shapes. For frontend use only.

##### models.ts
```TypeScript
...

export type LitClub = {
  id: string,
  name: string,
  ownerUserId: string,
  ownerUserName: string,
  description: string,
  preferredGenres: string[],
  memberUserIds: string[]
}
```

And while we're at it, let's go ahead and add a mapper for this domain model to `litclub-mappers.ts`.

##### litclub-mappers.ts
```TypeScript
...

type LitClubResponse = components["schemas"]["LitClubResponse"]

export function toDomainLitClub(dto: LitClubReponse): LitClub {
    return {
        id: dto.id!,
        name: dto.name!,
        ownerUserId: dto.ownerUserId!,
        ownerUserName: dto.ownerUserName!,
        description: dto.description!,
        preferredGenres: dto.preferredGenres!,
        privateClub: dto.privateClub!,
        memberUserIds: dto.memberUserIds!
    }
}
```

#### 3. Create a new service module

Creating a services module is useful because it abstracts interaction with the API (the `client` object) away from the UI implementation.

Right now, the services directory has the following structure:

```
/frontend         // Central module for API interaction
  /services
    booksService.ts
    librariesService.ts
    usersService.ts
    ...
```

The previous example was a little different—rather than creating `authService.ts` and placing it in the `services` directory, we created `auth/authContext`. This module is effectively equivalent to a service module, but with some added logic for authentication and session storage.

In most cases, you should just create a new service module.

##### litclubsService.ts
```TypeScript
import { client } from 'client';

// Import domain model
import { LitClub } from '../domain/models'

// Import frontend type and mappers
import { type AddLitClubInput, toAddLitClubRequest, toDomainLitClub } from '@/api-mappers/litclubs/litclubs-mappers';

export async function createLitClub(input: AddLitClubInput): Promise<LitClub | null> {
    try {
        // #1 Map the input to an AddLitClubRequest object
        const body = toAddLitClubRequest(input);

        // #2 Make API call with request body
        const { data, error } = await client.POST("/litclubs", { body });

        if (error) {
            // Parse status codes on error object
        }

        if (!data) {
            console.error('Unable to create LitClub.');
            return null;
        }

        // #3 Convert the response object to domain object
        return toDomainLitClub(data);

    } catch (err) {
        console.error('An unexpected error occurred:', err);
        throw err;
    }
}
```

#### File structure breakdown
```
/frontend
  client.ts             // Singleton client object
  
  /schema
    openapi-types.ts    // Backend-defined types

  /domain
    models.ts           // Contains LitClub domain model

  /api-mappers
    /litclubs           // Mapper functions for LitClubs
      litclubs-mappers.ts
    ...
  
  /services
    litClubsService.ts  // Interacts with API

  /app
    /createLitClub.tsx  // UI for creating LitClub
```

### Everything's wired up—now what?
In the file `createLitClub.tsx`, which contains the UI element for creating a LitClub, you will need to import the type `AddLitClubInput` and populate it with values from your form.

Next, you will call `createLitClub()`, imported from `litClubsService.ts`.

Then, you can use the returned domain `LitClub` type.

### In conclusion
The steps above provide a simple recipe for integrating your UI components with the backend API in a clean, efficient, and modular manner. By prioritizing organization from the very beginning, we will avoid many future headaches and prevent bugs from permeating the entire system.

It should be noted that you don't have to follow this recipe exactly. Use it as a reference for what good integration looks like.
